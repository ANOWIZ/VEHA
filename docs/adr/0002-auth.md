# ADR 0002 — Аутентификация и RBAC

## Статус
Принято.

## Контекст
Корпоративная аутентификация — Keycloak (OIDC) с федерацией в AD. Собственную
аутентификацию не изобретаем. При этом локальная разработка и автотесты не
должны требовать поднятого Keycloak.

## Решение
1. **Production**: backend валидирует access-token Keycloak — проверка подписи по
   JWKS realm (RS256), `iss`, `aud`, `exp`. Роли берутся из realm-roles
   (`realm_access.roles`). JWKS кэшируется в Redis/in-memory.
2. **Dev-fallback** (`AUTH_DEV_MODE=true`, только не-production):
   - `POST /api/v1/auth/dev-login` выпускает локальный HS256-токен с заданными
     ролями — для Swagger и фронта;
   - либо заголовок `X-Dev-User: <username>:<role1,role2>` — для быстрых curl/тестов.
   В production оба пути отключены жёстко (проверка `settings.environment`).
3. **RBAC** — FastAPI dependencies:
   - `get_current_user` — извлекает и валидирует пользователя из токена,
     синхронизирует/создаёт `User` при первом входе (JIT-provisioning);
   - `require_role(*roles)` — проверка наличия роли;
   - `require_project_access(...)` — проверка доступа к конкретному проекту
     (членство / роль pm/director/finance/admin).
   Права проверяются в зависимостях роутера, не в сервисах.

## Последствия
- Один и тот же код обработки идентичности в dev и prod, переключается флагом.
- Жёсткая защита: dev-пути физически недоступны при `ENVIRONMENT=production`.
